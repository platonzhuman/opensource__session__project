# Рубрика инженерного ревью

Одна и та же рубрика для самопроверки, взаимного ревью и защиты работы. Оценка —
не «нравится / не нравится», а severity и обоснование.

## Severity

| Уровень | Значение | Что делать |
| --- | --- | --- |
| `blocker` | нельзя принимать: неверный результат, утечка, невоспроизводимо | исправить до сдачи |
| `major` | существенный риск: нет baseline, нет error analysis, хрупкий код | исправить или явно принять риск |
| `minor` | качество: читаемость, структура, дублирование | исправить, если есть время |
| `nit` | вкусовое | по желанию |

## Рубрика

### 1. Постановка задачи

- [ ] Ясно, какое решение принимается и кем.
- [ ] Есть критерий успеха и критерий провала.
- [ ] Указаны ограничения: время, данные, стоимость, среда.
- [ ] Явно сказано, что **не** входит в задачу.

### 2. Протокол эксперимента

- [ ] Split зафиксирован до кода.
- [ ] Test не использовался при выборе модели.
- [ ] Baseline определён и посчитан.
- [ ] Метрики выбраны до эксперимента и обоснованы.
- [ ] Есть правило остановки.
- [ ] Зафиксированы seed и версии библиотек.

### 3. Данные

- [ ] Проверены пропуски, дубликаты, диапазоны, утечки.
- [ ] Понятно, как данные получены и можно ли их пересобрать.
- [ ] Есть проверка на сдвиг распределения (train vs val vs test).
- [ ] Нет признаков, которых не будет в проде.

### 4. Модель

- [ ] Начали с простого решения.
- [ ] Каждое усложнение обосновано измерением.
- [ ] Есть ablation: вклад изменений виден.
- [ ] Гиперпараметры выбраны на валидации.
- [ ] Модель интерпретируема настолько, насколько нужно задаче.

### 5. Оценка

- [ ] Метрика соответствует цели, а не удобству.
- [ ] Есть доверительные интервалы или разброс по фолдам.
- [ ] Есть error analysis по срезам.
- [ ] Проверена устойчивость к seed и малым изменениям.
- [ ] Отдельно описаны ограничения и режимы отказа.

### 6. Инженерия

- [ ] Код читается без устных пояснений.
- [ ] Нет мёртвого кода и закомментированных блоков.
- [ ] Функции названы по смыслу, побочные эффекты явные.
- [ ] Есть тесты на критичную логику.
- [ ] Ноутбук/скрипт запускается сверху вниз.
- [ ] Есть `requirements` или `environment`.
- [ ] Логи и артефакты не содержат секретов.

### 7. Решение

- [ ] Есть memo: ship / iterate / stop.
- [ ] Решение подкреплено числами.
- [ ] Указано, при каких условиях решение надо пересмотреть.
- [ ] Оценена стоимость поддержки.
- [ ] Назван следующий шаг, если решение отрицательное.

## Как писать замечание

Плохо: «тут плохо».

Хорошо:

```
[blocker] Утечка: target используется при выборе k
Где: 04-klasterizaciya.md, шаг 2
Почему: k подобран по ARI, тест перестаёт быть независимым
Как проверить: выбери k только по silhouette, пересчитай ARI
```

## Защита

На защите задаются три вопроса:

1. Почему это решение, а не более простое?
2. Откуда ты знаешь, что оно работает?
3. Что сломается первым и как ты это заметишь?
