# 3. PRIMARY KEY и UNIQUE

Этот урок — про уникальные коды. Именно их не хватало в первом скрипте, и именно
их требует домашка («у каждой записи — уникальный код»).

!!! abstract "Цель урока"
    Ты поймёшь, зачем нужен первичный ключ, чем он отличается от `UNIQUE` и как
    поймать нарушение уникальности.

## Шаг 1 · Зачем строке код

Строку нужно уметь отличать от других. Имя не подходит: сотрудников с одинаковым
именем может быть много. Нужен столбец, значение которого **никогда не повторяется**.

```sqlplay
-- @seed artillery
select id, name from employees order by id;
```

!!! question "Сделай"
    Чем `id` отличается от `name`?

??? success "Проверить"
    `id` — это код: он уникален для каждой строки и не зависит от текста. `name`
    может совпасть у двух разных людей.

## Шаг 2 · PRIMARY KEY — главный код таблицы

!!! note "Определение"
    **PRIMARY KEY** (первичный ключ) — столбец (или набор столбцов), значения
    которого уникальны для каждой строки и не могут быть пустыми (`NULL`).

В таблице может быть только **один** первичный ключ.

!!! question "Сделай"
    Попробуй вставить сотрудника с уже занятым `id = 1`. Что произойдёт?

```sqlplay
-- @seed artillery
insert into employees (id, name, birthday, military_rank_id)
values (1, 'Дубликат', '2000-01-01', 1);
```

??? success "Проверить"
    База вернёт ошибку уникальности первичного ключа. Вставить вторую строку с
    `id = 1` нельзя — это и есть защита.

## Шаг 3 · UNIQUE — уникальность без «главного» статуса

`UNIQUE` тоже запрещает повторы, но таких ограничений в таблице может быть много,
и `NULL` они обычно разрешают.

!!! tip "Правило"
    `PRIMARY KEY` = уникальность **и** запрет пустоты, ровно один на таблицу.
    `UNIQUE` = только уникальность, ограничений сколько угодно.

```sqlplay
-- @seed artillery
insert into units (id, base_unit_id, name, short_name)
values (99, 1, 'километр', 'м');
```

!!! question "Сделай"
    Почему этот `insert` падает, хотя `id = 99` новый?

??? success "Проверить"
    Потому что `short_name = 'м'` уже есть у единицы с `id = 1`, а на `short_name`
    наложено `unique`. Уникальность ломается, даже если первичный ключ новый.

## Шаг 4 · Найди ограничения таблицы

```sqlplay
-- @seed artillery
select constraint_name, constraint_type
from information_schema.table_constraints
where table_name = 'employees'
order by constraint_type;
```

!!! question "Сделай"
    Какие ограничения есть у `employees`?

??? success "Проверить"
    `primary key` на `id` и `foreign key` на `military_rank_id`. Внешний ключ разберём
    в следующем уроке.

## Шаг 5 · Составной ключ

!!! tip "Правило"
    Первичный ключ может состоять из нескольких столбцов: тогда уникальна их пара.

```sqlplay
-- @seed artillery
create table demo (a integer, b integer, constraint pk_demo primary key (a, b));
insert into demo values (1, 1);
insert into demo values (1, 2);
select * from demo order by a, b;
```

!!! question "Сделай"
    Почему вторая вставка прошла, хотя `a = 1` повторяется?

??? success "Проверить"
    Потому что уникальна **пара** `(a, b)`: `(1,1)` и `(1,2)` разные. Повтор `a`
    в одиночку допустим.

## Что здесь что

| Элемент | Что означает |
| --- | --- |
| `primary key (id)` | `id` — уникальный код строки |
| `unique (short_name)` | значения `short_name` не повторяются |
| `constraint ...` | имя ограничения, по нему видно его в ошибке |
| `information_schema` | системная таблица с описанием структуры |

## Откуда числа

`id = 1` уже занят — из данных `employees`. `short_name = 'м'` занят — из `units`.
Ошибки возникают из-за реальных данных, а не из-за выдуманных значений.

## Наивные вопросы

!!! question "Можно ли сделать первичным ключом `name`?"
    Технически можно, но плохо: имена повторяются, а если сотрудник сменит фамилию —
    придётся менять ключ и все ссылки. Для ключа берут неизменный код.

!!! question "Почему `PRIMARY KEY` не разрешает `NULL`?"
    Потому что ключ должен однозначно указывать на строку. Пустой ключ не указывает
    ни на что, поэтому запрещён.

!!! question "Чем `UNIQUE` полезен, если есть `PRIMARY KEY`?"
    Он держит уникальность второстепенных полей: например, чтобы две единицы не
    назывались одинаково (`'м'`).

## Чекпоинт

!!! question "Проверка"
    1. **Предскажи:** что вернёт `select id from military_ranks;` при попытке вставить
       вторую строку с `id = 2`?
    2. **Объясни**, чем `PRIMARY KEY` отличается от `UNIQUE`.
    3. **Напиши** ограничение, которое делает `name` сотрудника уникальным.

??? success "Проверить"
    1. Ошибку уникальности — `id = 2` уже занят (`Лейтенант`).
    2. `PRIMARY KEY` один на таблицу, запрещает `NULL`; `UNIQUE` — их много, `NULL`
       обычно разрешён.
    3. `constraint uq_employees_name unique (name)` внутри `create table` или
       `alter table employees add constraint uq_employees_name unique (name);`.

## Что дальше

Код уникален внутри своей таблицы. А как связать строки **разных** таблиц? Это
работа `FOREIGN KEY`.
