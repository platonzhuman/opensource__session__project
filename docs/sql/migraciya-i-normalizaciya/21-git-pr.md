# 21. Git-ветка и Pull Request

Последний шаг сдачи. Домашку оформляют отдельной веткой и отдельным Pull Request —
чтобы преподаватель видел ровно твои изменения.

!!! abstract "Цель урока"
    Ты создашь ветку, закоммитишь скрипт и откроешь Pull Request.

## Шаг 1 · Зачем отдельная ветка

Ветка — независимая линия изменений. Ты работаешь в ней, не трогая `main`. Потом
просишь влить её обратно — это и есть Pull Request.

!!! question "Сделай"
    Что произойдёт с `main`, пока ты работаешь в ветке `homework_two`?

??? success "Проверить"
    `main` не изменится. Твои коммиты лежат в `homework_two`, пока их не влили.

## Шаг 2 · Создай ветку

```bash
git checkout main
git pull
git checkout -b homework_two
```

!!! question "Сделай"
    Что делает `-b` в последней команде?

??? success "Проверить"
    Создаёт новую ветку `homework_two` и сразу переключается на неё.

## Шаг 3 · Положи файл и закоммить

Файл кладём в `_Infra/scripts/`, например `home_work_two.sql`.

```bash
git add _Infra/scripts/home_work_two.sql
git status
git commit -m "homework two: normalize params, add reference tables"
```

!!! question "Сделай"
    Зачем проверять `git status` перед коммитом?

??? success "Проверить"
    Чтобы убедиться, что в коммит попадут только нужные файлы, и не улетели лишние.

## Шаг 4 · Отправь ветку

```bash
git push -u origin homework_two
```

!!! question "Сделай"
    Что делает `-u`?

??? success "Проверить"
    Связывает локальную ветку с удалённой, чтобы потом хватало просто `git push`.

## Шаг 5 · Открой Pull Request

На странице репозитория появится кнопка **Compare & pull request**. Указываешь:
- **base** — `main` (куда вливаем);
- **compare** — `homework_two` (откуда);
- заголовок и описание: что сделано.

!!! question "Сделай"
    Что писать в описании PR?

??? success "Проверить"
    Коротко: какие справочники добавлены, как нормализованы параметры, что удалено,
    и приложить скриншот результата запроса. Без воды.

## Что здесь что

| Команда | Что делает |
| --- | --- |
| `git checkout -b имя` | создать и переключиться на ветку |
| `git add файл` | подготовить файл к коммиту |
| `git status` | показать, что изменилось |
| `git commit -m "..."` | зафиксировать изменения |
| `git push -u origin имя` | отправить ветку на сервер |

## Наивные вопросы

!!! question "Что если я забыл создать ветку и закоммитил в `main`?"
    Можно создать ветку от текущего состояния (`git branch homework_two`), перевести
    `main` назад (`git reset`) и продолжить. Лучше не доводить — создавай ветку сразу.

!!! question "Обязателен ли PR, если можно просто отправить файл?"
    Домашка требует PR. Он показывает историю и позволяет оставить комментарии.

!!! question "Что делать, если PR конфликтует с `main`?"
    Обновить ветку: `git checkout main && git pull && git checkout homework_two && git merge main`, разобрать конфликты, закоммитить.

## Чекпоинт

!!! question "Проверка"
    1. **Предскажи:** изменится ли `main` после `git push origin homework_two`?
    2. **Объясни**, зачем проверять `git status` перед коммитом.
    3. **Напиши** команды: создать ветку `homework_two`, добавить файл, закоммитить.

??? success "Проверить"
    1. Нет, пока PR не влит — `main` не тронут.
    2. Чтобы не закоммитить лишние файлы и понимать, что уйдёт в коммит.
    3. `git checkout -b homework_two` → `git add _Infra/scripts/home_work_two.sql` →
       `git commit -m "homework two"`.
