# 5. Нормализация: 1НФ, 2НФ, 3НФ

Это ядро домашки. Первый скрипт хранил параметры «широкой» таблицей, и именно это
надо исправить. Урок объясняет, что значит «нормально» и почему.

!!! abstract "Цель урока"
    Ты поймёшь три нормальные формы и увидишь, какая из них нарушена в
    `measurment_input_params`.

## Шаг 1 · 1НФ: атомарные значения

!!! note "Определение"
    **1НФ** (первая нормальная форма): в каждой ячейке одно значение, а не список;
    нет повторяющихся групп столбцов.

Посмотри на таблицу параметров первого скрипта.

```sqlplay
-- @seed base
select * from measurment_input_params;
```

Пять столбцов `height`, `temperature`, `pressure`, `wind_direction`, `wind_speed` —
это однотипные факты (измеренные значения), разложенные по столбцам.

!!! question "Сделай"
    Что придётся сделать, чтобы добавить новый параметр, например «влажность»?

??? success "Проверить"
    Изменить структуру таблицы: `alter table ... add column humidity ...`. Данные и
    код запроса придётся переписывать при каждом новом параметре. Это признак того,
    что модель неудобна.

## Шаг 2 · 1НФ на практике: одна строка — один факт

Правильнее хранить **одно измеренное значение в одной строке**.

```sqlplay
-- @seed artillery
select measurment_bath_id, parameter_type_id, value
from measurment_input_params
where measurment_bath_id = 1
order by parameter_type_id;
```

!!! question "Сделай"
    Сколько строк описывают пачку `1`?

??? success "Проверить"
    5 строк — по одной на каждый параметр. Один факт = одна строка.

## Шаг 3 · 2НФ: не зависеть от части ключа

!!! note "Определение"
    **2НФ**: таблица в 1НФ, и каждый не-ключевой столбец зависит от **всего**
    первичного ключа, а не от его части. Это важно, когда ключ составной.

В нашей таблице параметров ключ простой (`id`), поэтому 2НФ выполняется автоматически.

!!! question "Сделай"
    Почему для `measurment_input_params` 2НФ не проблема?

??? success "Проверить"
    Ключ — один столбец `id`. «Части» ключа нет, значит частичной зависимости быть
    не может.

## Шаг 4 · 3НФ: не-ключ не должен зависеть от другого не-ключа

!!! note "Определение"
    **3НФ**: таблица в 2НФ, и ни один не-ключевой столбец не зависит от другого
    не-ключа. Такая зависимость называется **транзитивной**.

Здесь и спрятана ошибка «единица измерения внутри параметра». Единица зависит от
**типа параметра**, а не от конкретного измерения.

```sqlplay
-- @seed artillery
select p.name as параметр, u.short_name as единица
from parameter_types as p
inner join units as u on u.id = p.unit_id
order by p.id;
```

!!! question "Сделай"
    Зависит ли единица измерения от конкретной пачки? Объясни.

??? success "Проверить"
    Нет. У параметра «Высота» единица всегда `м`, у любой пачки. Значит, хранить
    единицу рядом с измерением — лишнее дублирование. Её место — в справочнике
    `parameter_types` → `units`.

## Шаг 5 · Собери модель

Итоговая модель домашки:

- `base_units` — физические величины (Длина, Температура…);
- `units` — единицы (`м`, `°C`…), ссылаются на базовую величину;
- `parameter_types` — параметры, ссылаются на единицу;
- `measurment_input_params` — измерения, ссылаются на тип параметра.

!!! question "Сделай"
    Посмотри, как связаны справочники, и назови связь `units → base_units`.

```sqlplay
-- @seed artillery
select b.name as величина, u.name as единица, u.short_name
from units as u
inner join base_units as b on b.id = u.base_unit_id
order by u.id;
```

??? success "Проверить"
    Связь «один-ко-многим»: у одной базовой величины (`Длина`) может быть много
    единиц (`м`, позже `км`). Обратно — каждая единица принадлежит ровно одной
    величине.

## Что здесь что

| Элемент | Что означает |
| --- | --- |
| 1НФ | одна ячейка — одно значение |
| 2НФ | не-ключ зависит от всего ключа |
| 3НФ | не-ключ не зависит от другого не-ключа |
| транзитивная зависимость | `измерение → тип параметра → единица` |
| `base_units → units → parameter_types` | иерархия справочников |

## Откуда числа

5 столбцов и 5 строк — из первого скрипта (`height`…`wind_speed`) и из нормализованных
данных. Единицы `м`, `°C`, `мм рт. ст.`, `б. д. у.`, `м/с` — из справочника `units`.

## Наивные вопросы

!!! question "Нормализация — это всегда хорошо?"
    Для учебной базы — да. В аналитике иногда сознательно денормализуют ради скорости,
    но это осознанный компромисс, а не ошибка проектирования.

!!! question "Сколько нормальных форм существует?"
    В теории больше (4НФ, 5НФ, 6НФ), но на практике почти всегда хватает 3НФ. Дальше
    начинаются редкие случаи.

!!! question "Почему единица в отдельной таблице, а не строкой в `parameter_types`?"
    Чтобы одна единица не повторялась текстом и её можно было переиспользовать. Плюс
    так единица связана с физической величиной.

## Чекпоинт

!!! question "Проверка"
    1. **Предскажи:** что придётся менять, чтобы добавить параметр «Влажность», в
       широкой модели и в модели EAV?
    2. **Объясни**, что такое транзитивная зависимость на примере единиц измерения.
    3. **Напиши** запрос: список параметров и их единиц (короткие имена).

??? success "Проверить"
    1. В широкой — структуру (`alter table add column`). В EAV — только данные
       (`insert` в `parameter_types` и `measurment_input_params`).
    2. Единица зависит от типа параметра, а тип — от измерения: `измерение → тип →
       единица`. Единицу нельзя вешать на измерение.
    3. `select p.name, u.short_name from parameter_types p inner join units u on u.id = p.unit_id order by p.id;`
