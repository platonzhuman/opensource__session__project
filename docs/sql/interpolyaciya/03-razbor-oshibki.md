# 3. Разбор классной ошибки

В классе запрос возвращал не тот отрезок: для 26° вместо `25–2 / 30–3.5`
получалось `40 / 4.5 / пусто / пусто`. Разбираемся, почему, — и учимся такое
ловить заранее.

!!! abstract "Цель урока"
    Ты поймёшь, почему имена столбцов в подзапросе «перепутались с условием»,
    и будешь проверять запросы трассировкой.

## Шаг 1 · Код, который написали в классе

```sql
select x0, x1, y0, y1
into v.x0, v.y0, v.x1, v.y1
from (
	select temperature as x0,
	       correction  as x1,                                     -- вот тут
	       lead(temperature) over (order by temperature) as y0,
	       lead(correction)  over (order by temperature) as y1
	from calc_temperature_correction
) t
where x0 >= par_temperature
  and (x1 <= par_temperature or x1 is null)                       -- и тут
order by x1 desc
limit 1;
```

## Шаг 2 · Что реально лежит в столбцах `t`

| строка | `x0` | `x1` | `y0` | `y1` |
| --- | --- | --- | --- | --- |
| (0, 0.5) | 0 | **0.5** | 5 | 0.5 |
| (5, 0.5) | 5 | **0.5** | 10 | 1 |
| … | … | … | … | … |
| (40, 4.5) | 40 | **4.5** | NULL | NULL |

`x1` — это **корректировка**, а не следующая температура. А `y0` — наоборот,
следующая температура. Имена перепутаны местами.

Само по себе это не смертельно: `into v.x0, v.y0, v.x1, v.y1` раскладывает
значения по порядку, и поля структуры в итоге получались правильными
(`v.y0 ← x1` — корректировка и т.д.). Засада — в `where` и `order by`: они
написаны «по именам», а имена не соответствуют смыслу.

## Шаг 3 · Читаем условие словами

Подставь смысл каждого столбца:

> «температура ≥ t и корректировка ≤ t»

Это бессмысленное условие: сравнивать корректировку с температурой нельзя.

Для 26°: температура ≥ 26 — подходят строки `(30, 3.5)` и `(40, 4.5)`;
«корректировка ≤ 26» — верно для всех. Кандидаты — те же две строки.

А `order by x1 desc` сортирует по **корректировке**: `4.5 > 3.5`, поэтому
побеждала строка 40. Отсюда и результат `40 / 4.5 / NULL / NULL` почти для
любой температуры.

## Шаг 4 · Полная трассировка для 26°

| строка | `x0 ≥ 26`? | `x1 ≤ 26`? | проходит | `x1 desc` |
| --- | --- | --- | --- | --- |
| (0 … 25) | нет | да | нет | — |
| (30, 3.5) | да | да | **да** | 3.5 |
| (40, 4.5) | да | да | **да** | **4.5 → победитель** |

А почему для 2° «случайно работало»? Условие «корректировка ≤ 2» отсекало все
строки с поправкой больше 2. Оставалась `(25, 2)` — и структура получалась
верной. Совпадение.

## Шаг 5 · Как ловить такие ошибки

1. **Имена = смысл.** Температура — это `x`, корректировка — `y`. Хочется
   написать `correction as x1` — стоп.
2. **Проговаривай условие словами** уже после подстановки смысла: «корректировка
   ≤ 26°» видно сразу.
3. **Трассировка.** Возьми одну температуру, выпиши кандидатов, прогони условие
   и `order by` вручную. Одна минута — и ошибка найдена.
4. **Сверь с проверенным правилом** из урока 2: `x0 ≤ t` и (`x1 > t` или
   `x1 is null`), сортировка по `x0`.

!!! warning "Мораль"
    Для SQL `x1` — просто имя столбца, оно ничего не значит. Смысл держишь в
    голове ты, и только ты отвечаешь за то, что сравниваешь то, что хотел.

## Наивные вопросы

!!! question "А если бы имена были правильные, но условие осталось таким же?"
    Всё равно ошибка: условие сравнивает не те величины. Имена помогают
    заметить ошибку, но не исправляют её автоматически.

!!! question "Почему для 26° возвращалось `40/4.5/пусто/пусто`, а не ошибка?"
    SQL честно выполнил то, что написали. Ошибка была не в синтаксисе, а в
    смысле — такие ошибки не «падают», они тихо врут.
