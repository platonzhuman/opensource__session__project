# 7. Сборка: один `do $$` и вложенные транзакции

Собираем всё в два файла: DDL-скрипт и проверочный скрипт. Важно: учитель
требует, чтобы DDL был **одним** блоком `do $$` с вложенными транзакциями —
именно так устроен его собственный `20261014.sql`.

!!! abstract "Цель урока"
    Ты соберёшь DDL в один `do $$` с вложенными транзакциями, напишешь
    проверочный скрипт отдельным файлом и подготовишь скриншот.

## Шаг 1 · Один блок, а не несколько

Наивно можно сделать так: отдельный `do $$` для типа, а функции — просто
`create function` рядом. Или три отдельных блока. Учитель в ревью такое
возвращает:

> «Все в один `Do$$` блок включить. Сделать вложенные транзакции.»

Поэтому весь DDL — внутри одного `do $$`.

## Шаг 2 · Вложенные транзакции: каркас

Внутри `do $$` шаги разделяют вложенными блоками `begin … end;` и `commit;`:

```sql
do $$
begin
	begin
		-- шаг 1
	end;
	commit;

	begin
		-- шаг 2
	end;
	commit;
end $$;
```

Каждый `commit;` фиксирует свой шаг. Это и есть тот самый шаблон «транзакция в
транзакции», который учитель показывал в `20261014.sql`.

!!! question "Сделай"
    Сколько `commit;` будет в скрипте из четырёх шагов?

??? success "Проверить"
    Четыре — после каждого вложенного блока.

## Шаг 3 · Наш скрипт по шагам

Внутри `do $$` — четыре вложенные транзакции:

1. **Очистка** прошлой версии — чтобы скрипт можно было запускать повторно:

   ```sql
   drop type if exists public.interpolation_type cascade;
   ```

   `cascade` заодно удалит и функции, которые зависят от типа.

2. **Тип** `interpolation_type` (x0, y0, x1, y1).

3. **Функция поиска отрезка** по температуре.

4. **Функция расчёта** интерполяции (с защитой от деления на ноль).

!!! question "Сделай"
    Почему `drop type ... cascade` удаляет и функции?

??? success "Проверить"
    Функции зависят от типа (принимают/возвращают его), поэтому `cascade`
    удаляет зависимые объекты.

## Шаг 4 · Теги: почему `$body$`

Внешний блок — `do $$`, а тела функций — в `$body$ … $body$`. Если написать
`$$` и там, и там, внешний блок «закроется» на первом же внутреннем `$$` —
скрипт развалится с синтаксической ошибкой.

!!! warning "Проверено на практике"
    С одинаковыми тегами Postgres выдаёт `syntax error at or near "select"` —
    парсер обрезает блок раньше времени.

## Шаг 5 · Запуск и повторный запуск

Скрипт запускается **целиком на верхнем уровне** — как обычный запрос в
pgAdmin (Execute). Не оборачивай его в `begin; … commit;`: внутри `do $$`
`commit` в таком случае упадёт с `invalid transaction termination`.

Запусти скрипт дважды — оба раза должно пройти без ошибок (это и есть проверка
повторного запуска).

!!! question "Сделай"
    Что должно произойти при втором запуске DDL-скрипта?

??? success "Проверить"
    Старые тип и функции удалятся (drop … cascade), новые создадутся — ошибок нет.

## Шаг 6 · Проверки — отдельным скриптом

Замечание учителя одногруппнику: **тестирование — отдельным скриптом**. У нас
так и задумано: второй файл `home_work_five_check` — это `do $$` с проверками
(26°, узлы, границы) и `raise notice` в конце.

## Наивные вопросы

!!! question "Можно ли сделать всё вообще без `do $$`?"
    Можно было бы `begin; create type…; create function…; commit;` — но задание
    просит именно PL/pgSQL-скрипт, и учитель требует эту форму. Не спорь с
    шаблоном.

!!! question "А если один из шагов упадёт?"
    Упадёт весь запуск; предыдущие `commit;` уже зафиксированы. Поэтому шаги
    делают независимыми: очистка → тип → функции.
